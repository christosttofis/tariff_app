# Security Remediation Checklist

Follow-on hardening items identified during the 2026-07-14 architecture/security review (`TECHNICAL_ARCHITECTURE_REVIEW.md`) and the subsequent XSS deep-dive. Tracked separately from that review because these are forward-looking action items, not findings about current code.

- [x] **1. DOMPurify for the notices rich-text rendering path.** ~~The admin notices editor (assumptions/legal/vulnerable-customer text, EN/EL) intentionally renders raw HTML on `customer.html` — a WYSIWYG feature, not a bug, but it means a compromised admin account (or a rich-text-editor bug) has a direct stored-XSS path to the public page.~~ **Fixed 2026-07-14.** Vendored DOMPurify 3.1.6 (same cdnjs pattern already used for Chart.js) in both `customer.html` and `admin.html`. Sanitized at all 4 sinks: `customer.html`'s `switchNoticesTab()` (assumptions/legal tabs) and `openVulnerableModal()` (vulnerable-consumer info popup) — the two actual public/unauthenticated exposure points; and `admin.html`'s `setNotices()` (display into the rich-editor divs) and `getNotices()` (read back before POSTing to the backend) — so a payload can't round-trip through the admin's own editor either, and what actually gets saved server-side is already sanitized (defense-in-depth on top of item 3's future server-side validation). Verified live: seeded a disposable SQLite DB with `onerror`/`onload` payloads in `assumptions_en`/`legal_en`/`vulnerable_en`, loaded both real pages via Playwright — 0 fires across all 3 customer.html sinks and the admin.html editor round-trip, markup (`<p>`/`<img>`/`<svg>`) preserved, dangerous attributes stripped, 0 console errors.
- [x] **2. Content-Security-Policy header.** **Fixed 2026-07-14 — permissive variant shipped.** Added a `Content-Security-Policy` response header via Starlette middleware in `tariff-api/main.py` (`add_csp_header`), applied to every response (static HTML/JS/CSS and API responses alike). Policy: `script-src`/`style-src` allow `'unsafe-inline'` plus the two CDN hosts actually used (`cdnjs.cloudflare.com` for Chart.js/DOMPurify, `fonts.googleapis.com`/`fonts.gstatic.com` for Roboto); everything else is locked down — `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'self'`, `connect-src 'self'` (no external fetch/XHR exist in any of the 3 portals, confirmed by grep), `img-src 'self' data:`. **`'unsafe-inline'` was kept deliberately** — the frontend is ~hundreds of inline `onclick="..."` handlers plus inline `<script>` blocks (the entire app logic, not just handlers), so a strict CSP would require refactoring all of that to `addEventListener`/external scripts first; that refactor is not scheduled. This means the CSP does **not** block the class of bug fixed in items 1 and the earlier XSS pass (inline-handler/inline-script injection) — it only guards against loading *external* malicious scripts/styles and locks down framing, forms, plugins, and cross-origin connections. Verified live: loaded all 3 portals (customer/admin/supplier) via Playwright with the header active — 0 console/page errors, Chart.js and DOMPurify still load from cdnjs, admin login (a same-origin fetch) still works, fonts still render.
- [x] **3. Server-side input validation on tariff/supplier submissions (`tariff-api/schemas.py`).** **Fixed 2026-07-14.** Rewrote `tariff-api/schemas.py`:
  - `TariffIn.contract`/`voltage`/`pricing`/`fpaSource`/`loadEntitlement` and `TariffStatusIn.status`/`MessageIn.audience`/`ScheduledNotificationIn.audience` are now Pydantic `Literal[...]` types matching the exact value sets used by each frontend `<select>` (verified against `supplier.html`'s dropdowns and `routers/admin.py`'s `_VALID_STATUSES`) — a raw API call with a valid JWT can no longer set an arbitrary string in these fields.
  - Added `max_length` to every free-text field (`name` 200, `licence` 100, `address`/`website` 500, `email` 254, `tel` 50, profile `desc` 2000, message `subject` 200/`body` 20000, notices HTML fields 50000, rejection `reason` 1000) and `ge`/`le` bounds on `durationMonths` (1-120) and `interval_months` (1-60).
  - `SupplierIn.email` and `CreateUserIn.email` now go through the `email-validator` library (added to `requirements.txt`) via a shared `_check_email` validator — empty string still allowed (field is optional), but a non-empty value must be a well-formed address.
  - `SupplierIn.website` now goes through a `_check_url` validator requiring an `http://`/`https://` scheme — this is the root-cause fix for the `javascript:` URL bug from the XSS pass: a supplier can no longer *submit* a `javascript:`/`data:` URL in the first place, not just have it neutralized at render time by `safeUrl()`.
  - `rates`/`discounts` deliberately left as loosely-typed JSON (`dict[str, Any]`/`list[Any]`) — their shape varies by `pricing` type (Fixed/ToU/Dynamic/Variable each need different keys) and wasn't in scope for this pass; flag if you want a follow-up item for per-pricing-type nested schemas.

  Verified live against the real running app (disposable SQLite DB, real admin JWT): valid supplier/tariff submissions still succeed (201), a supplier with `website: "javascript:alert(1)"` + `email: "not-an-email"` is rejected 422 with both errors listed, and a tariff with `contract: "HackedType"` is rejected 422 naming the 3 valid literals.

- [x] **4. Reduce `innerHTML` reliance in favor of `textContent`/DOM node construction, especially at the highest-risk sinks.** **Fixed 2026-07-14.** Rewrote all 3 highest-severity sinks in `admin.html` to build real DOM nodes instead of HTML template-literal strings:
  - **`renderLoginActivity()`** — each row (`<tr>`/`<td>`) is now built with `document.createElement`, untrusted fields (`r.email`, `r.reason`, `r.ip_address`, `r.user_agent`) set via `.textContent`/`.title`, replacing the table body with `tbody.replaceChildren(...rows)`.
  - **`buildDashboard()`'s pending-review widget** — same pattern; the tariff name/supplier line is set via `.textContent`, and the "Review" button is now bound with `addEventListener` + a closure over `t.id` instead of embedding the id in an inline `onclick="openReview('${t.id}')"` string.
  - **`openReview()` (the tariff review modal)** — the whole modal body is now assembled as DOM nodes via a `row()` helper and a `multilineSpan()` helper (replaces `.replace(/\n/g,'<br>')` with real `<br>` elements between text nodes). Covers all fields: name/contract/voltage/pricing/profile/discounts (plain `textContent`) and the changed-field diff view (`ch.from`/`ch.to`, also `textContent`) — including the rates diff, which now uses real DOM line breaks instead of an HTML string.
  - Also removed two now-redundant `esc()` calls inside `formatRatesSummary()` (its output is only ever consumed by the new `textContent`-based `multilineSpan()` now, so escaping there was pointless post-refactor and would have shown literal `&lt;`/`&gt;` instead of the intended characters in the rare case a rate's month/kWh field contained one).
  - None of these 3 sinks depend on `esc()` being called correctly anymore — the DOM structure itself guarantees untrusted values can only ever be text, never markup.
  - Scope note (unchanged from the original assessment): this was a targeted rewrite of the 3 most severe sinks, not a wholesale rewrite of all ~116 `innerHTML` sites across the 3 portals — the remainder still rely on `esc()`, which is applied everywhere and was verified live in the earlier XSS pass.

  Verified live: seeded a disposable SQLite DB with `onerror`/single-quote-breakout payloads in the tariff name, supplier name, discount label, profile name, and changelog diff (`from`/`to`) fields, plus an unauthenticated login attempt with a malicious email/User-Agent. Loaded the real admin.html, triggered the dashboard widget, clicked its live "Review" button (not calling `openReview()` directly) to open the modal via its real event handler, and loaded the login-activity table. 0 fires across 8 payload flags, 0 console errors, 0 dialogs — all payloads rendered as inert text.
