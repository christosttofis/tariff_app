# Security Remediation Checklist

Follow-on hardening items identified during the 2026-07-14 architecture/security review (`TECHNICAL_ARCHITECTURE_REVIEW.md`) and the subsequent XSS deep-dive. Tracked separately from that review because these are forward-looking action items, not findings about current code.

- [ ] **1. DOMPurify for the notices rich-text rendering path.** The admin notices editor (assumptions/legal/vulnerable-customer text, EN/EL) intentionally renders raw HTML on `customer.html` — a WYSIWYG feature, not a bug, but it means a compromised admin account (or a rich-text-editor bug) has a direct stored-XSS path to the public page. Add DOMPurify as a client-side dependency and sanitize `notices.*` HTML before it's set via `innerHTML` in `customer.html` (and anywhere `admin.html` previews it), allowing the formatting tags actually used (bold, links, headings, lists) and stripping everything else (`<script>`, event handler attributes, etc.).
- [ ] **2. Content-Security-Policy header.** Currently absent entirely (confirmed: no CSP middleware in `main.py`, no `<meta>` CSP tag in any of the 4 HTML files). Needs a decision first: ship a permissive CSP (`'unsafe-inline'` for scripts) as partial defense-in-depth now, or refactor the ~hundreds of inline `onclick="..."` handlers across `admin.html`/`supplier.html`/`customer.html` to `addEventListener` bindings first so a strict CSP (no `'unsafe-inline'`) can actually block inline-script/inline-handler injection. The strict option is the only one that would have caught the class of bug fixed in this session; the permissive option is much cheaper but mainly guards against loading *external* malicious scripts, not inline injection.
- [ ] **3. Server-side input validation on tariff/supplier submissions (`tariff-api/schemas.py`).** Checked 2026-07-14: none of the Pydantic schemas constrain their fields — this is a distinct gap from the XSS fixes (those were output-encoding failures; this is a missing input layer). Specifically:
  - `TariffIn.contract`/`voltage`/`pricing`/`fpaSource`/`loadEntitlement` are plain `str`, though each is meant to be one of a fixed set of values enforced only by the frontend `<select>` dropdown — a raw API call with a valid supplier JWT can set any string. (`tariff.status` is the one field actually validated, via `_VALID_STATUSES` at the router level.)
  - No `max_length` anywhere — `name`, `supplier`, `licence`, `address`, message `subject`/`body`, etc. accept unbounded strings.
  - `email` fields are plain `str`, not `EmailStr` — no format validation.
  - `website` has no URL/scheme validation server-side — this is *why* the `javascript:` scheme bug in item priorities above was possible in the first place; the display-side fix (`safeUrl()`) is done, but nothing stops a supplier from submitting a `javascript:` URL to begin with.
  - `rates` (`dict[str, Any]`) and `discounts` (`list[Any]`) accept arbitrary JSON shapes with no schema enforcement.

  Recommended fix: convert the enum-like string fields to Pydantic `Literal[...]` types, add `max_length` to free-text fields, switch `email` fields to `EmailStr`, and add a URL-scheme validator (`http`/`https` only) to `website`. This is defense-in-depth, not an active exploit path today (the output-encoding fix already closes the XSS risk) — but it shrinks what a malicious/compromised supplier account can get stored in the first place, and is a second line of defense if any future render site is ever added without going through `esc()`.

- [ ] **4. Reduce `innerHTML` reliance in favor of `textContent`/DOM node construction, especially at the highest-risk sinks.** Checked 2026-07-14: `textContent` is already the more common pattern overall (222 uses across the 3 portals vs. 116 `innerHTML` uses), and no site was found using `innerHTML` for a *pure* single escaped value with no surrounding markup (i.e. no case where `textContent` would be a drop-in replacement today) — every `innerHTML` site bundles the data together with static markup (badges, buttons, table rows), which is why it can't just be swapped 1:1. `createTextNode` is not used anywhere, but that's a non-issue: `textContent =` is the modern equivalent with no safety difference, and it's already the dominant idiom here.
  The real gap this points to: because data-plus-markup is built as one HTML string, every one of those 116 sites *depends on remembering* to call `esc()` correctly — there's no structural guarantee. A `createElement`-based rewrite of the handful of highest-risk sinks (the tariff review modal, the dashboard pending-review widget, the login-activity table — the three most severe findings from the XSS pass) would build the static badges/buttons as real DOM nodes and set the untrusted parts via `textContent`, removing reliance on `esc()` for those specific text nodes entirely. This is a larger refactor than items 1–3 and lower priority given `esc()` is now applied everywhere and verified live — worth doing for the 3 highest-severity sinks specifically, not a wholesale rewrite of all 116.
