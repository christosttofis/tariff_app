# Database migrations

Schema migrations, managed by Alembic (replaces the old create_all() +
hand-rolled ALTER TABLE block that used to live at the top of main.py).

## How it runs

main.py calls `alembic upgrade head` at every startup, so day-to-day usage
(start.bat, seed_demo_data.py) needs no manual migration step — the app
brings its own database up to date automatically, the same way the old
ALTER TABLE block did, just with a real version history behind it.

## Adding a schema change

1. Edit the relevant model in `models.py`.
2. From `tariff-api/`, with your venv active:

   ```bash
   alembic revision --autogenerate -m "short description"
   ```

3. **Read the generated file in `migrations/versions/` before running it** —
   autogenerate is a draft, not gospel. It won't detect: renamed columns (it
   sees these as a drop + an add, which loses data — write these by hand),
   changes to server-side defaults on existing columns, or the kind of
   one-time data backfill baseline_schema's upgrade() does for
   `password_changed_at`. Add any needed `op.execute(...)` data migration by
   hand alongside the autogenerated `op.add_column(...)`.
4. Test it: run the app against a scratch SQLite copy of a database that
   already has the *previous* migration applied, confirm `alembic upgrade
   head` applies cleanly, and that `alembic downgrade -1` reverses it without
   errors.
5. Commit the migration file alongside the model change, in the same commit —
   a model change with no matching migration file will drift real databases
   out of sync with what the code expects.

## Bringing an existing database under Alembic without re-running history

The `09e5a0ba9353_baseline_schema.py` migration represents the schema as it
stood the day Alembic was introduced (2026-07-23) — every table and column
that previously existed via create_all() + the old ALTER TABLE statements.
A database that already has this schema (e.g. the real dev Postgres instance)
must be told "you're already here" rather than have the migration re-run
against tables that already exist:

```bash
alembic stamp head
```

This only writes a bookkeeping row (which migration has been applied) — it
does not touch schema or data. A brand new/empty database (a fresh SQLite
file, a demo database, a future production instance) does not need this step;
just run `alembic upgrade head` (or start the app normally) and it builds the
schema from scratch.
